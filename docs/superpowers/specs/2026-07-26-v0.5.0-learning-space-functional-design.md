## 3. Canonical semantic tree

DOM/source order 固定如下；wide scene 只能用 CSS placement 改构图，不能改读屏/Tab 顺序：

```text
StudyRoute
└─ StudySpaceDocument
   ├─ header: StudyContextHeader
   │  ├─ BackToChat (existing safe escape; E2 may later enrich state)
   │  ├─ SpaceSwitcher
   │  ├─ DraftInboxLink
   │  ├─ GovernanceLink
   │  └─ AskNanaLink / CupAnchor
   ├─ nav: StudyLifecycleNav (five canonical links)
   ├─ status: refresh / stale / offline / conflict / interrupt
   └─ main: StudyPageRegion
      ├─ h1 + page status summary
      ├─ PrimaryTaskRegion
      ├─ EvidenceRegion
      ├─ RelatedActionRegion
      └─ optional aside: ContextualSummary
```

Rules：

1. `header → nav → status → main → aside` is the accessible order at every width.
2. Exactly one `main` and one page `h1`; async refresh status is polite, mutation/error is assertive only when
   user action requires it.
3. Object wrappers are optional decoration. Removing all scene CSS/assets leaves the complete tree usable.
4. No scene object intercepts browser back, space switch, dirty guard or Tutor interrupt; it calls the same
   repository/navigation action as the flat control.
5. S-1 may introduce view models, but their fields must be derived only from existing repository results plus
   E2/X2 handoff. It may not add a scene-only API.

## 4. Container-query and flat fallback contract

Study owns a named container, not viewport-specific business branches:

| Container state | Semantic presentation | Prohibited behavior |
|---|---|---|
| `>= 60rem` | header/nav/main/aside may occupy three visual zones; DOM order unchanged | canvas-only hit targets or spatial-only instructions |
| `40rem..59.999rem` | main + stacked aside; lifecycle links wrap or self-scroll | hiding a lifecycle page or draft/governance action |
| `< 40rem` | one document column; all controls full label, minimum focus target; tables self-scroll | hamburger-only lifecycle, clipped labels, two-axis page scroll |
| 200% / forced-colors / screen reader | flat document semantics are authoritative | requiring paper texture, color, drag, hover or animation to understand state |
| reduced motion | no spatial/flip/steam/view-transition dependency | delaying state visibility until animation completes |
| scene chunk/asset failure | same flat tree remains mounted; one non-blocking diagnostic allowed | blank stage, route fallback, data refetch loop |

S-1 readiness tests must force flat mode independently of viewport so semantic equivalence is directly testable.
Visual scene assets and V tokens are absent from the S-1 base chunk.

## 7. State matrix

| State | Existing/future source | Required presentation | Mutation/navigation rule |
|---|---|---|---|
| idle/loading | request coordinator | labelled status/skeleton with stable landmark | no duplicate request from scene mount |
| ready | repository result | exact data; no invented progress | actions use repository/service only |
| empty | successful bounded query | explain what is absent and one valid next action | never render fixture/demo as user data |
| refreshing | previous + new request | previous stays visible, polite refresh status | stale generation cannot commit |
| stale | previous + failed refresh | label retained data and retry | no auto navigation or reset |

| invalid/not-found | route/service validation | no existence leak across owner/space | canonical safe target only |

## 9. Whiteboard S-2 frozen contract

### 9.1 Storage ownership

S-2 uses the existing `learning.db` owner/space boundary and the common cross-process LearningStore operation
fence. It does not use browser localStorage, workspace files, Tutor checkpoint JSON, or a second database.

- mutable working state: one validated `learning_items` record per `(owner, space, activity_id)` with revision CAS;
- immutable save: `whiteboard_snapshot` Learning Output artifact, initially draft;
- explicit attach: trusted user action activates a validated snapshot and records only bounded hash/id evidence;
- restore: copies a selected owned snapshot into working state as the next CAS revision; snapshot remains immutable;
- export: canonical JSON to an explicit user-chosen file; PNG/preview is derived and never canonical state;
- delete: removes selected working/snapshot content under the common fence, then performs the same WAL/main-file
  compaction discipline as sensitive learning delete. Hash-only activity evidence may remain; it contains no scene.

S-2 must add exact public store/service methods; raw callers may not write arbitrary item state or bypass caps.

### 9.2 Exact scene schema

`whiteboard_snapshot` uses Learning Output Envelope v1 and deterministic review. Payload exact shape:

```json
{
  "schema_version": 1,
  "activity_id": "bounded opaque id",
  "lineage_id": "bounded opaque id",
  "revision": 1,
  "parent_artifact_id": null,
  "scene": {
    "schema_version": 1,
    "elements": []
  },
  "scene_sha256": "64 lowercase hex"
}
```

Each element has exact common fields plus a type-specific geometry:

```json
{
  "element_id": "stable bounded id",
  "type": "text|math|line|arrow|rectangle|ellipse",
  "x": 0,
  "y": 0,
  "tone": "ink|accent|muted|warning",
  "stroke_width": 1,
  "width": 120,
  "height": 40,
  "content": "required for text/math; absent for shapes"
}
```

`text|math` require `width/height/content`; `rectangle|ellipse` require `width/height` and forbid content;
`line|arrow` require `end_x/end_y` and forbid width/height/content. These are discriminated exact shapes, not one
bag of optional fields.

Validation rules：

- exact fields; unknown keys rejected at every level;
- maximum 256 elements, 2,000 codepoints per text/math content, 32,000 total content codepoints;
- canonical scene JSON maximum 240 KiB and full envelope maximum 256 KiB, leaving headroom inside the existing
  512 KiB generic envelope cap;
- identifiers 1..128 ASCII safe characters; coordinates/endpoints finite integers in -10,000..10,000,
  width/height 1..20,000; stroke width enum 1..4;
- element ids unique; revision positive integer; parent belongs to same owner/space/lineage and revision-1;
- max 8 immutable snapshots per activity, 3 MiB canonical whiteboard bytes per activity, 4 MiB per space,
  8 MiB per owner. Quota check and write share one coordinated transaction;
- envelope source refs max 32 for this kind and must use existing bounded scalar form.

Hard denylist: image/blob/data/http/file URLs, HTML, SVG/path data, arbitrary CSS/color/font, JS, event handlers,
iframes, embeds, plugins, external fonts, executable code and unknown element types. Math content is rendered by
KaTeX with errors shown as text; it is never evaluated.

### 9.3 Write, idempotency and crash recovery

Every working save request binds owner/space/activity/lineage, expected revision, idempotency key and canonical
scene fingerprint:

- write-ahead request identity and validated scene commit are coordinated before success is returned;
- same identity + same fingerprint returns the committed revision; same identity + different payload conflicts;
- stale expected revision conflicts without overwrite; concurrent writers have one winner;
- UI may debounce command groups for at most 500 ms, but shows “已保存” only after the host commit response;
- restart restores the last committed revision/hash. At most the visibly unsaved debounce group can be lost and
  must not be called recovered;
- snapshot/attach/export/delete are separate idempotent operations. A crash cannot leave an activated artifact
  without a validated immutable envelope.

### 9.4 Export, import and deletion budgets

- Whiteboard bytes are included in the existing learning owner sub-bundle and its 16 MiB cap; composite
  StudyOwnerBundleV2 remains 24 MiB. The 8 MiB owner whiteboard quota reserves room for non-whiteboard learning data.
- Export/import validates quota, hashes, owner/space refs, lineage and parents before first write. Near-cap round trip
  and over-cap zero-write tests are mandatory.
- JSON export is UTF-8 canonical state. PNG may be generated at max 2,048×2,048 from the already validated scene;
  it is not imported as editable truth and is outside app-data secure delete once the user saves it elsewhere.
- Per-snapshot delete refuses when an active attachment or descendant still references it unless the user chooses a
  bounded cascade whose exact target ids are previewed. No recursive directory deletion is used.

### 9.5 Dependency gate

S-2 default is ordinary DOM/SVG primitives plus the already locked KaTeX. No whiteboard framework is needed for the
v0.5 allowlist. A future dependency proposal must separately record exact locked version/integrity, license and
transitive licenses, unpacked/runtime gzip delta, install-script/native/WASM/network behavior, advisory scan,
WebView2 Windows input/zoom/IME/accessibility smoke and lazy-chunk proof. Any failure keeps DOM+KaTeX; it does not
trigger a rushed custom canvas or raise the bundle warning limit.

## 10. Performance and loading budgets

- `/chat` initial graph delta from S-1/S-2: 0 bytes of reachable Study/whiteboard code.
- S-1 StudyRoute gzip delta: <=12 KiB relative to 32,539 bytes, excluding later V assets.
- Whiteboard editor: separate route/activity lazy chunk, target <=90 KiB gzip with existing shared KaTeX excluded;
  it loads only for an explicit whiteboard activity.
- No full-scene JSON in list/summary calls; summary returns ids, revision, counts, bytes, hash and timestamps only.
- Lists are paged: max 50 whiteboard summaries, max 8 snapshots/activity. Rendering virtualizes or chunks only if
  measured 256-element DOM exceeds the WebView2 frame budget; semantic element list remains available.
- S-1/S-2 must record raw+gzip deltas and 200%/IME/reduced-motion/forced-colors evidence; raising Vite warning
  thresholds is not an acceptance mechanism.
