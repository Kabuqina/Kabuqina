> **状态：** `OWNER DIRECTION CONFIRMED · PROTOTYPE UPSTREAM`

> **不包含：** Studio 内部工具、编辑器形态、具体输出格式和生产实现方案。Studio 的详细

## 0. 决策摘要

### 0.1 一句话产品模型

> **Study 让知识在自己身上重新长出来，Studio 让理解走向别人。**

**机制修订（2026-07-25，owner）：**"输入"只描述方向（知识向内），不描述机制。人的
Study 不是机械输入，而是在心智里重构知识——把知识在自己身上再创造、再体验一遍。因此：

- Study 界面不得堆砌输入信息；默认只呈现当前一步最关键的知识核，随后立即转入引导
  （学习者自己解释、推导、尝试），呈现是引子，重构动作才是主体；
- 学习页的基本单元是"知识核 → 学习者动作 → 对照反馈"的循环，不是可通读的正文；
  学习页不是阅读器；
- 材料与资源只作为被引导按需调用的参考，不作为铺开的主线；
- 学习证据只能是重构行为的痕迹（答案、解释、推导、修正）；"已读 / 已浏览"不构成
  证据，不改变掌握度。

Kabuqina v0.5.0 的两个产品内核是：

- **Study：输入与内化。** 用户围绕课程接收材料、理解内容、练习、修正、复习和评估；
- **Studio：输出与表达。** 用户围绕项目组织观点、选择来源、形成结构、迭代表达并产生
  可传播或可交付的作品。

这不是简单的“学习页面 + 文件生成页面”。两者分别拥有不同的容器、对象、完成标准和
历史：

| 领域 | 用户发生的变化 | 主容器 | 核心对象 | 完成标准 |
|---|---|---|---|---|
| Study | 外部信息转化为用户的理解与能力 | Course / 课程本 | 材料、活动、答案、笔记、卡片、评估、学习证据 | 用户完成学习动作，证据可解释 |
| Studio | 用户的理解与材料转化为外部表达 | Project / 项目 | Brief、来源快照、结构、版本、作品、交付物 | 表达目标成立，作品可审阅、导出或分享 |

### 0.2 “学习成果”与“交付物”分离

原先“制作 / 成果”的设计把两类对象混在了一起，现予以修订：

- **学习证据（Learning Evidence）**属于 Study：答案、练习记录、评估、笔记、反思、
  知识卡片和掌握度变化；
- **作品 / 交付物（Work / Deliverable）**属于 Studio：演示文稿、讲义、报告、文章、
  海报、网页、音视频脚本或未来其他表达形式；
- PPT 是 Studio 的一种输出格式，不是 Studio 的定义，更不是学习成果的默认代表；
- Studio 交付物不能反向证明“已经学会”，也不能自动修改掌握度、计划完成度或练习状态。

### 0.3 v0.5.0 的首要任务

v0.5.0 的首要任务是**前端产品架构重构**，不是把旧页面重新上色，也不是堆叠功能数量。
重构过程中允许并需要：

- 新增支撑新架构的能力；
- 调整、迁移或删除旧功能；
- 重命名含混对象；
- 重新定义导航、上下文、返回和恢复；
- 将暂不成熟的能力降为连接验证，而不是伪装成完整中心。

### 0.4 完整结构不等于全部可见

v0.5.0 可以建立完整的领域结构、状态与连接，但单个界面不得同时展示这些结构。界面默认只
呈现：

1. 当前任务；
2. 完成任务所需的必要上下文；
3. 一个清楚的下一步动作。

P2 辅助信息与 P3 解释性信息在当前版本先砍掉，不保留折叠入口；只有被真实任务证明为必要的
信息，才可重新定义为 P1。产品架构说明、原型旅程、调试状态和完整对象关系不能泄漏为普通
用户必须阅读的界面内容。详细信息预算和反 overdesign 规则见
`2026-07-25-v0.5.0-interface-information-principles.md`。

## 1. 产品层级

### 1.1 两个业务域

目标产品以 Study 和 Studio 作为两个稳定业务域：

```text
Kabuqina
├─ Study  输入与内化
│  ├─ 课程
│  ├─ 材料
│  ├─ 学习活动
│  ├─ 学习证据
│  └─ 复习与评估
└─ Studio 输出与表达
   ├─ 项目
   ├─ Brief / 表达目标
   ├─ 来源快照
   ├─ 结构与版本
   └─ 作品 / 交付物
```

### 1.2 两个跨域层

Chat 与 Activity 不再被视为第三、第四个业务域：

- **Chat 是交互层。** 全局入口默认提供未绑定的自由会话；用户主动选中历史会话后，才根据
  显式作用域表现为课程辅导或项目协作；
- **Activity 是状态层。** 它投影 Study 与 Studio 中正在运行、等待、中断、失败、完成或
  可恢复的活动。

界面可以保留 Chat 与 Activity 的全局入口，但信息架构不得让用户误解为四个等权应用。

## 2. 领域职责

### 2.1 Study：输入与内化

**负责：**

- 建立和维护课程；
- 读取并引用课程材料；
- 计划、学习、练习、检查、修正、复习与评估；
- 保存用户答案、笔记和学习证据；
- 从具体学习现场发起课程 Chat，并精确返回；
- 作为可被 Studio 显式取用的素材来源（取材由 Studio 发起，Study 自身不提供向外的出口）。

**不负责：**

- 管理外部表达项目；
- 把 PPT、报告或其他文件当作学习掌握度；
- 在课程本中承载完整制作流程；
- 自动把 Studio 输出写成课程知识；
- 用“成果”一词同时指代学习证据和交付物。

### 2.1.1 课程材料从哪来（2026-07-26 owner 决定）

三条路径在代码中都已存在，但**主次必须明确**，否则会滑向内容供给业务：

| 路径 | 定位 | 现状 |
|---|---|---|
| **学生自己导入** | **默认路径** | docling 已接入（PDF/DOCX/PPTX/XLSX/MD/HTML/CSV/图片） |
| 产品自带课程 | **样板（onboarding demo），不是内容服务** | `hermes_core/learning/builtin_courses/python_advanced.py`，仅一门 |
| 小娜生成 | **加工，不是来源** | 知识库/资源包等一律先进草稿箱待审核 |

**为什么默认是学生导入：**这门产品的对象是"有自己教材的学生"。他手上那本教材才是老师要考
的东西；我们提供的任何"标准教材"都在和它竞争且必然落败。

**为什么内置课程只做样板：**一旦定位成"我们提供课程内容"，就等于承诺教研——学科覆盖、
版本更新、错误修订、与各校教材对齐、著作权处理。那是另一门生意，与"学习 agent"的内核无关。
因此**保持一门，明确标为示例**，力气全部投入导入体验。

**为什么小娜不能凭空写材料：**产品的全部证据链（复印件、出处、来源可追溯）都建立在"材料有
真实来源"之上。没有来源的材料会让整套物性谎报。她可以从**学生给的材料**里抽知识点、编卡片、
出题——这些已强制走草稿箱审核。

既有实现已经体现了这个尺度：内置课程 seeder 是 trusted caller，但**只有闪卡与测验直接激活；
计划、知识库、资源包仍停在 draft 等学生审核**。

**对界面的要求：**材料必须标明来源——`origin: imported` 显示「你导入的 · 文件名 · 页码」，
`origin: builtin` 显示「产品自带的示例」。两者可信度来源不同，不能混为一谈。

### 2.1.2 多份材料如何形成一个目录（2026-07-27 owner 决定）

学生一次导入两份以上材料（教材 + 习题集 + 讲义 + 真题）时，目录怎么形成、学习怎么组织。

**先说这条要守住什么。**目录之所以可信，是因为它**整理既有结构，不凭空生成关系**（§2.1.1），
界面上还写着「小娜从《…》整理」。多文件最大的诱惑就是让小娜合成一棵统一主题树——那句
provenance 立刻变成谎话，而且学生无法核对某个节是从哪来的。

**否决的三种做法：**

| 做法 | 否决理由 |
|---|---|
| 多份目录并排 | 学生自己对账；正是"把因果关系拆散"，且一屏塞多棵树 |
| 小娜合成主题树 | 可信基础作废，目录退化成猜测 |
| 学生选一本、其余当附件 | 诚实但浪费；习题集与真题正是练习和评估的素材来源 |

#### 定稿：一根骨架 + 可核对的挂靠

**骨架**＝某一份**真实文件**的章节结构（通常是教材或教师讲义）。目录仍然只来自一份文件，
`origin` 与「小娜从《…》整理」一个字都不用改。

**其他文件挂到骨架的节上。**每条挂靠是一个**可核对的断言**——「习题集 p.41 → §2.3」，
学生点开两边就能验证。这是全部关键：agent 的产出从**发明结构**变成**声明对应**，
而对应是可证伪的，发明不是。挂靠另标「小娜认为对应」，与骨架的 provenance 分开显示。

**挂不上的不强行挂。**留在书堆里显式标注"还没对上"，既不硬塞进某一节，也不藏起来——
藏起来等于替学生决定它没用。

#### 学习怎么组织：一个目录，每节下挂着不同**角色**的材料

多文件的真正价值是让学习循环有真实素材，而不是多几棵树：

| 角色 | 典型文件 | 进循环的哪一步 |
|---|---|---|
| 讲解 | 教材、讲义 | 知识核 → 引导重构 |
| 练习 | 习题集 | 练习 |
| 检验 | 真题、试卷 | 评估 |
| 参考 | 手册、公式表 | 按需翻，不进主线 |

角色同样可核对（一份全是题的文件就是练习源），同样由小娜判、学生确认。

#### 骨架谁选：小娜提名 + 学生确认

小娜看哪份有真实可抽的结构、且其他文件都能挂上去，**提名一份并说理由**
（"它有 12 章目录，且其他三份都能挂上去"），学生一步确认或换一份。
学生不必从零判断——他导进来的可能是一堆扫描件和无名 PDF，未必知道哪份才有目录；
但最终话语权在他。

#### agent 要做四件事，每件都可核对

1. **分课**——这些是不是同一门课？学生很可能一次拖进整学期文件夹。不是就拆成不同课程本，
   不硬凑一个目录。
2. **选骨架**——提名 + 理由。
3. **对齐并定角色**——逐项挂靠，给出可核对的理由。
4. **落不下的显式留白**——不强配。

#### 红线

1. **挂靠与角色都是草稿，必须学生确认**，走知识点/卡片同一条草稿箱通道，不自动生效；
2. **绝不发明任何一份文件里都不存在的节**；
3. **不因为没对上就隐藏文件**；
4. **仍然不出现覆盖率**——"4 份材料已对齐 80%" 是同一个陷阱换皮（§2.1.1 与目录红线一致）。

#### 顺序冲突：骨架管结构，计划管时间

教师讲义的顺序常常不等于教材顺序（跳章、合并、加内容）。**顺序差异落在计划层**
（本周学哪节），**不重排目录**。否则目录会随讲义漂移，而目录是学生唯一稳定的坐标系。

### 2.2 Studio：输出与表达

**负责：**

- 建立独立 Project；
- 明确受众、目的、表达目标、限制与完成标准；
- 接受来自 Study、Chat 或本地文件的显式来源快照；
- 组织结构、版本、协作过程与作品；
- 保存可找回、可追溯、可继续的输出状态；
- 导出、打开、分享或回到来源。

**不负责：**

- 判断用户是否学会；
- 修改 Study 的掌握度、计划或练习；
- 成为 PPT 专用生成器；
- 在整体布局冻结前承诺自由画布、时间线、页面编辑器或某种具体创作范式；
- 将普通 Chat 的文本或文件路径猜测为已归档作品。

### 2.3 Chat：自由会话空间与跨域交互层

Chat 会话有三种来源与作用域：

| 会话来源 | 主要职责 | 写入边界 |
|---|---|---|
| Study | 解释、提示、追问、检查理解并返回学习现场 | 只产生建议或待审核学习草稿 |
| Studio | 梳理目标、结构、表达和修改方向 | 只修改当前项目草稿或产生待审核方案 |
| Chat 自由会话 | 开放问题、临时任务和未归类思考 | 不自动写入 Study 或 Studio |

完整 Chat 的主要用途是自由会话。用户从全局入口进入时，默认进入未绑定 Course 或 Project
的自由会话，而不是 Study / Studio 的聚合首页，也不自动恢复最近一个领域会话。

来自 Study 与 Studio 的会话只作为普通历史会话存在于 Chat 中，与自由会话使用同一历史列表
和排序规则。它们可以带低强调的来源标签用于辨认，但不建立专属分区、推荐位、仪表盘或
“Study / Studio / 自由会话”三个并列的高权重入口。只有用户主动选中历史会话，完整 Chat
才进入相应作用域，并显示完成当前对话所必需的最小来源与返回信息。

Study 和 Studio 右下角的“小娜”是保留当前工作面的轻量上下文聊天框；完整 Chat 是独立、
极简的自由会话界面。两种 presentation 必须复用同一
session/context/transcript/composer/pending 真值，不建立 mini-chat 副本。用户可以从轻量
聊天框显式打开当前会话的完整视图，但这不改变全局 Chat 入口默认进入自由会话的规则。

### 2.4 Activity：跨域状态层

Activity 负责：

- 显示所有正在进行和可恢复活动；
- 明确活动属于 Study 还是 Studio；
- 保留中断原因、checkpoint、重试和返回目标；
- 在重启后让用户选择恢复哪个现场；
- 当返回目标失效时安全降级到正确 Course 或 Project。

Activity 不负责定义课程、项目或作品语义。

## 3. 整体布局

### 3.1 稳定导航

宽屏 Product Shell 推荐：

- 中央主导航：**Study / Studio**；
- 全局交互：**Chat**；
- 全局状态与设置：**Activity / Settings**。

这样布局直接表达：

- Study 与 Studio 是两个业务空间；
- Chat 随时可用，默认承载自由会话，但不是业务对象容器；
- Activity 是全局状态投影。

从全局导航打开 Chat 时，默认进入自由会话；来自 Study / Studio 的会话必须由用户从历史中
主动选择。全局 Chat 不因当前位于 Study 或 Studio 而自动切换作用域。

窄窗必须保留相同语义，不得因折叠变成不同的信息架构。

### 3.2 Study 空间

书桌母版按物化原则修订如下：

- 桌沿：书立。课程名长在本子自己的标签上，换课＝换一本本子；不再保留常驻的课程栏与材料栏
  （材料改为学习页内按需调用）；
- 桌沿最右：杂记本。它不是课程，因此离开课程那一组单独放置；
- 中央：打开的课程笔记本；
- 右侧：本课复习卡片盒；
- 右下：小娜杯；
- 移除笔记本下方完整“制作 / 成果工作夹”；
- **Study 侧不提供任何向外的出口。**学习就是纯粹的学习；跨域取材一律由 Studio 发起
  （见 §4.1）。课程 Chat 同属 Study，同样不提供“发送到 Studio”。

### 3.3 Studio 空间

本轮只冻结整体布局，不冻结内部工具：

- 左侧：项目册，负责切换项目和新建项目；
- 中央：当前 Project 的稳定工作面，优先呈现 Brief、来源、当前阶段和下一步；
- 右侧：来源与连接，显示来自 Study、Chat 或文件的可追溯快照；
- 可从项目内进入 Studio Chat；
- 不在本轮决定中央工作面最终是画布、编辑器、时间线、页面列表或其他形态。

Studio 应与 Study 使用同一产品 shell、纸张/书桌视觉母语和状态语言，但不伪装成课程本。

## 4. Study ↔ Studio 连接合同

### 4.1 显式取材（由 Studio 发起）

唯一默认连接方式是用户在 **Studio 侧**发起的显式取材。方向很重要：Study 不向外推送，
Studio 在需要素材时来取。

```text
在 Studio Project 中发起“从 Study 取素材”
  → 选择要取用的学习内容
  → 预览将取走什么
  → 创建只读 SourceSnapshot
  → 回到该 Studio Project
```

自由 Chat 是唯一的例外：它不属于 Study，其内容可由用户显式发送到 Studio。

### 4.2 SourceSnapshot

转交对象至少包含：

- 稳定来源 ID；
- 来源类型与标题；
- 来源 Course、page、activity 或 Chat session；
- 用户选择的内容快照；
- 创建时间与 revision；
- 可用的 return target；
- 删除或失效后的 fallback target。

Studio 引用快照，不拥有或改写 Study 原对象。

### 4.3 返回与回链

- Studio 中每个来源可返回原 Course / page / activity；
- 原目标失效时只降级到正确 Course，不跳到别的课程；
- Studio 作品可作为课程“参考材料”建立链接，但不能自动变成学习证据；
- 同一对象不得在两个领域分别拥有可冲突的可变副本。

## 5. 核心对象

| 对象 | 真值所有者 | 说明 |
|---|---|---|
| `Course` | Study | 一门持续学习的课程 |
| `LearningActivity` | Study | 学习、练习、复习、评估活动 |
| `LearningEvidence` | Study | 用户行动产生的学习证据 |
| `StudioProject` | Studio | 一项表达或交付目标的容器 |
| `SourceSnapshot` | Shared relation | 跨域只读来源快照 |
| `StudioWork` | Studio | 项目中的结构、草稿或作品 |
| `Deliverable` | Studio | 可审阅、导出或分享的版本化输出 |
| `ChatSession` | Chat | 带显式作用域的会话 |
| `ActivityRecord` | Activity | 跨域运行、等待与恢复投影 |
| `ReturnTarget` | Shared relation | 精确返回或安全 fallback |

## 6. 原型旅程修订

全产品 Canonical 原型按以下旅程调整：

| Journey | 目的 | 终态 |
|---|---|---|
| J1 | 第一次进入 → 开课程 → 开始输入与学习 | Study Course 建立 |
| J2 | Study 当前步骤 → Course Chat → 精确返回 | 原答案、反馈和焦点未丢失 |
| J3 | General Chat → 审核 → 保存为学习草稿 | Study 获得待审核对象 |
| J4 | Study 选择内容 → 审核快照 → Studio Project | 来源已转交，领域真值未混写 |
| J5 | Study 与 Studio 多现场 → 重启 → 用户选择恢复 | 恢复正确 Course 或 Project |

原 J4“选材料 → 生成 PPT → 成果”不再作为全产品主旅程。具体 Studio 生产旅程应在 Studio
单独设计后新增，不得继续把 PPT 流程代表为 Studio 本身。

## 7. v0.5.0 范围

### Must

- 稳定的 Study / Studio 双域 Product Shell；
- Chat 默认自由会话、三类会话统一历史与显式作用域切换；
- Study 已冻结学习主路径与课程 Chat exact return；
- Studio Project 最小容器与来源关系；
- Study → Studio 显式转交；
- ordinary Chat 不隐式写入任一领域；
- restart 后多个 Course / Project 现场可区分、可恢复；
- 宽屏、窄窗、键盘与读屏语义等价。

### Deferred

- Studio 详细工作面；
- PPT、文档、网页、音视频等格式的专属流程；
- 自由画布、时间线、页面编辑器或自动排版范式；
- 完整模板市场、共享素材库或协作发布；
- 以某一种输出格式倒推整个 Studio IA。

## 8. 不变量

1. Study 真值只由用户学习动作和明确审核写入；
2. Studio 输出不自动修改学习状态；
3. Chat 永远显示当前作用域，不猜测隐式 Course / Project；
4. 跨域连接必须生成可见、可追溯的 SourceSnapshot；
5. 所有深层活动都有明确 ReturnTarget；
6. Activity 可以投影状态，但不拥有领域对象；
7. PPT 只是 Studio 的一种潜在交付物；
8. 在 Studio 详细设计冻结前，原型只承诺布局、容器和连接。
9. 单个界面只呈现 P0 当前任务和 P1 必要上下文；P2、P3 在当前版本先砍掉。
10. 全局 Chat 默认进入自由会话；Study / Studio 会话仅作为普通历史存在，只有用户主动选择
    后才进入对应作用域。
11. Study 是重构不是输入：界面先呈现最关键知识核再引导学习者动作；"已读 / 已浏览"
    永远不构成学习证据。
