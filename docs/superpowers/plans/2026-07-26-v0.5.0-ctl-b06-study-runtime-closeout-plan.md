## 1. Frozen implementation order

### Phase A · L-3 exact branch contract

- Add pure `TutorCheckSpecV1`, pinned rubric/next-unit refs, deterministic evaluation result and
  `tutor-branch-v1` policy.
- Only `submitted|correct|incorrect|invalid` plus host-pinned metadata may branch.
- Preserve L-2 acknowledgement path unchanged; old checkpoints validate/migrate without guessed rubric.
- Missing/stale/hash-drift source becomes `blocked(source_missing)`; legacy partial score is never a predicate.
- Golden matrix covers complete/advance/remediate/hint/blocked/invalid, one-remediation cap and provenance.

### Phase B · L-3/P-2 runtime integration

- Introduce explicit activity mode/check spec in start request; ordinary Tutor start stays participation-only.
- Resolve activated quiz item and grader provenance under owner/space before create; persist only pinned refs.
- On resume, grade through existing QuizService deterministic truth and store a bounded evaluation result;
  graph consumes the pure policy decision, not model prose.
- Level ④ hint is an explicit action through B04 zero-call service; direct full solution remains user-owned.
- Level ⑤ uses one structured practice/teach activity and B04 review-only evaluation draft boundary. A production
  evaluator may be wired only through a dedicated single-physical-attempt provider port with durable reservation;
  it never calls ordinary `call_llm()`.

### Phase C · L-5 retention and budgets

- Store bounded learner-evidence records: answer fingerprint, outcome/evidence codes, and a separately bounded raw
  learner excerpt only when required for current remediation; no source document or secret.
- Retention policy keeps unresolved check/current learner error/branch reason; compresses repeated Tutor prose and
  materialized old observations.
- Tutor, semantic evaluator and post-node usage remain separate numeric buckets. Compression itself performs no
  unreserved model call; deterministic truncation is the baseline.
- Golden long-activity tests prove the learner error survives into remediate input.

### Phase D · L-4 kq-kp v2 post-node

- Post-node accepts only bounded visible assistant output after raw-block stripping.
- Deterministic rule extractor is the zero-call baseline; optional cheap model path requires its own reservation.
- Output is the existing candidate schema and still requires explicit capture; it never auto-writes learning fact.
- Desktop, Gateway, export and TTS all consume clean visible text and never expose fenced raw block.
- H1 prompt gate remains until parity evidence is complete; retirement is a final commit, not mixed with rollout.

### Phase E · S-2 whiteboard runtime

- Implement the S-0 exact `whiteboard_snapshot` contract, item CAS, idempotency, quotas, lineage and immutable saves.
- Use existing learning DB + common writer/owner operation fence; no new database or browser persistence.
- Add trusted desktop source APIs for working save/load, snapshot/restore/attach/export/delete; no Web editor yet.
- DOM/SVG+KaTeX is the declared consumer; no dependency/package/bundle change.
- Export/import/delete/near-cap/concurrency/crash tests prove the frozen 16/24 MiB composition remains coherent.

### Phase F · S-3 Tutor whiteboard port

- Versioned allowlisted element commands only; model cannot emit JS/SVG path/URL/plugin data.
- Validate and preview every proposed mutation before CAS; rejected command does not advance checkpoint.
- Save/snapshot/attach/cancel/recover bind the same Tutor activity/revision and do not create a second activity graph.
- Whiteboard failure returns readable Tutor/check and preserves learner answer.
