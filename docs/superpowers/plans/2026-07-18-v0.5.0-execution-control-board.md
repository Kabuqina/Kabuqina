# v0.5.0 执行总控板：三流并行、Gate 驱动与派工规则

> **性质：** v0.5.0 的派工与集成控制面。本文不增加功能范围，不替代各专项计划，
> 只把既有路线压缩成可分配的工作包、WIP 上限、依赖门、共享热区和 release blockers。
>
> **状态：** Active v1（2026-07-18）。状态栏只按可核验交付物更新；“已有详细计划”、
> “进入设计”或“完成若干代码”均不自动等于 Gate 通过。
>
> **版本目标：** 交付一个成熟、可理解、可恢复、可升级的 Study-first 产品；不以
> “route 已存在”“平台从 UI 隐藏”或“hero 图很好看”代替产品完成。

## 0. 如何使用本文件

### 0.1 权威顺序

发生冲突时按以下顺序裁决：

1. owner 已冻结的产品/渠道决定；
2. [v0.5.0 开发计划](2026-07-17-v0.5.0-development-plan.md)的版本范围和 release 门；
3. E/C/X/V/L/P/S/R 等专项计划的领域合同；
4. 本文件的当前派工、WIP 和 merge train；
5. 每个运行时切片开工前单独编写的 JIT implementation plan。

本文可调整“谁先做、谁等待、谁合并”，但不能静默改变专项计划已经冻结的产品或数据
语义。范围或合同变化必须回写上游计划/`DECISIONS.md`，然后再更新本板。

本文派工卡统一使用 `CTL-A* / CTL-B* / CTL-C* / CTL-G*`；不带 `CTL-` 的 E/C/L/P/S/X/V/R/Q
编号始终指专项计划原始 slice。例如 `CTL-C04` 是总控板的长尾删除工作包，原计划 `C-4`
仍专指 credential/job/home-channel 兼容，二者不得混用。

### 0.2 状态词

| 状态 | 含义 |
|---|---|
| `READY` | 前置证据已具备，可立即分配；尚未开始 |
| `ACTIVE` | 已有唯一负责人、明确 base commit/worktree 和交付物 |
| `REVIEW` | 交付物与证据已提交，等待指定 Gate reviewer 验收 |
| `BLOCKED` | 缺少硬前置或出现 stop-rule；必须写明解除条件 |
| `WAITING` | 已知前序尚未完成，不应提前开工 |
| `DONE` | Gate reviewer 已按退出证据验收，不是作者自报完成 |
| `PARKED` | 不占 v0.5.0 当前活动槽；恢复时必须做等量 scope swap |

不使用模糊百分比。一个工作包只有“尚未满足退出证据”或“已满足并验收”。

不是持续增加功能的第四条线。

## 3. WIP 与派工硬规则

1. **全局最多 3 个产品工作包 ACTIVE：每条执行流最多 1 个。** 先完成或阻塞转交，
   才从同一流的 `NEXT` 拉取下一项。
2. `CTL-G00` 是 part-time release stewardship，不算第四个功能包；如果它需要实际代码修改，
   该修改占用 C 流的活动槽。
3. 每个工作包只有一个 accountable owner；协作者可以多人，但不能有两个最终裁决者。
4. 运行时代码开工前必须有独立 JIT plan、base commit、允许路径、禁止热区、测试命令、
   回滚/兼容说明和退出证据。
5. 一个共享热区同一时间只有一个 owner。消费者从已记录的固定 commit 起步，不从他人的
   dirty worktree 复制文件。
6. 机械删除、schema/行为语义变化、scene UI 与依赖/bundle 收口分 commit、分 review。
7. Gate 只认测试、截图/原型记录、schema/manifest、构建物和 reviewer sign-off；
   不认“应该可以”“看起来完成”或作者自己的完成声明。
8. 发现 P0、安全/数据丢失风险、静默改投、隐式 course binding 或无法升级时立即停止该
   slice，不用临时 fallback 掩盖。

## 6. C 轨的受控并行方式

C-0 → C-1 → removal → C-4 是硬顺序，但 removal 叶子可受控并行：

```text
CTL-C01 manifest
    └── CTL-C02 stop-producing/autostart
            ├── CTL-C03a Discord adapter/tests
            ├── CTL-C03b Feishu/Lark adapter/tests
            ├── CTL-C03c WeCom adapter/tests
            ├── CTL-C04a SMS/Twilio
            ├── CTL-C04b Slack/Signal/Matrix/Mattermost
            ├── CTL-C04c BlueBubbles/Home Assistant/Yuanbao
            ├── CTL-C04d Webhook/API server
            └── CTL-C04e IRC/Teams plugins
                    ↓
              CTL-C05 shared closeout
                    ↓
              CTL-C07 compatibility + release
```

并行条件：

- 每个 leaf 独立 worktree、独立 adapter/tests commit；
- leaf owner 不修改 shared registry/profile/requirements/bundle；只提交需要 integrator 收口的
  patch list；
- C integrator 独占 shared spine 并维护 merge train；
- 若平台删除必须先重构 shared helper，先由 integrator 落一个中性 helper base commit，
  所有 leaf 从该 commit 重新起步；
- CTL-C06 retained readiness 可做 adapter-local 验证，但涉及 shared profile、Rust supervisor、
  requirements/bundle 的修改仍由 integrator 排程。

## 9. Release blockers

以下任一未关闭，v0.5.0 不得宣称“成熟产品”或进入正式 release：

- E4、X4、V5 无可引用 sign-off，或 J1-J5/Study task 仍有 P0；
- Tutor M7、Practice M8、确定性 grader、interrupt/resume/restart 未形成真实闭环；
- `state.db`/`learning.db` migration、owner/space/CAS 或 v0.4 upgrade 不安全；
- SEA 仍回落 mainland，或 Python/Rust/Web/bundle retained set 不一致；
- 钉钉仍是“源码保留但 SDK/transport disabled”，或任一 retained 渠道没有 profile smoke；
- removed 平台仍有 live source、route、dynamic import、依赖、runtime package、credential
  autostart、network host 或 bundle/license surface；
- 旧 job/home target 被静默改投，或旧 credential 会自动启动/扩网；
- public/branded build、installer、Windows WebView2、a11y、性能、安全、隐私门未关闭；
- feature complete 后仍进行 schema migration、平台大删除或 scene architecture 变更。

## 12. 更新与回报节奏

- **分配时：** 填 owner、base commit、worktree、状态 `ACTIVE`；同时锁定热区 owner。
- **发生变化时：** 只更新状态、阻塞条件、证据链接和下一卡，不重写专项计划内容。
- **进入 REVIEW：** 必须附 commit、测试数字、构建/原型证据和已知风险。
- **验收后：** Gate reviewer 标 `DONE`，release captain 更新 merge train 的
  `base commit → consumer branches → integration result`。
- **每次拉 NEXT：** 先检查全局 WIP=3、同流 WIP=1、前置 Gate、热区冲突和 v0.4 merge gate。
- **稳定窗口：** 只接受 release blocker 修复；任何新功能回到 U/PARKED。
