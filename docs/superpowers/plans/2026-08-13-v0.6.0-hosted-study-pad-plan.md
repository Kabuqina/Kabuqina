## 0. 一句话

0.6.0 不是"给桌面端套个平板壳"，而是**把 Study 学习内核从本地单机形态，重构为

## 2. 范围

### 目标受众与学科范围

**定位：通用学习 agent，不是数学/代码专用产品。** 覆盖受众最广的自学场景：

| 受众段 | 核心科目 |
|---|---|
| 高中 | 语文、数学、外语 |
| 大学通识 | 高等数学、英语 |
| 考研 | 数学、英语（核心） |
| 考公 | 申论等文科内容；行测含数量关系、资料分析 |

**对技术选型的关键含义**：**数学贯穿全部受众段**（高中数学 / 高等数学 / 考研数学），
且高数与考研数学是**公式最密集**的内容类型，其教学形态是**多行推导**。
因此公式渲染质量是**一级产品需求**，而非细节——详见 §4.1。

**代码学习不在 0.6.0 范围内**（需专门开发，另行立项）。

### 产品立场：纸负责动手，平板负责引导

**这是 0.6.0 的定位命题，不只是功能取舍。**

诚实的前提：**平板在"做数学"上没有优势，甚至是劣势。** 数学学习拆成三段后，
平板只在中间一段上弱——而那一段本就不该数字化：

| 环节 | 谁更强 | 说明 |
|---|---|---|
| **看懂**（讲解、例题演示、多行推导展开） | **平板** | 屏幕大、可回放、可追问、可展开细节；纸无法自适应讲解 |
| **动手**（自己推导、演算、草稿） | **纸，压倒性** | 零延迟、无限空间、不挑姿势。平板在此全是劣势 |
| **回顾**（错题本、公式定理复习、间隔重复、薄弱点） | **平板，压倒性** | 纸质错题本翻不动、不会提醒、不会按遗忘曲线安排 |

**决定性论据——考试介质本身是手写的。** 目标受众是高考、考研、考公，
**这些考试全部纸笔手写作答**。因此"在纸上练"不是妥协，而是**正确的训练**；
让学生在平板上写数学反而是为错误的介质做训练（手感、速度、排版习惯均与考场不符）。

由此，"平板不能替代纸"从**缺陷**转为**产品定位**：

> **纸负责动手，平板负责纸做不到的事**——讲解、适应、记忆、安排复习、分析错误。

这与 README 的产品铁律"**学习者动手，她引导**"完全一致：学生在纸上动手，agent 在平板上引导。

**非数学科目不存在此张力**：语文、英语、申论（阅读、词汇、范文、结构分析）本就是平板强项。
该矛盾仅存在于数学一科，并由下述"拍照桥梁"化解。

### 一级能力：拍照批改 + 错题本（由上述立场直接推出）

纸留在纸上，则两者之间需要一座桥——**摄像头**：

```
学生在纸上做题 → 拍照 → 服务端公式识别 / OCR → agent 批改讲评 → 错题入复习队列
```

- **复用既有能力**：`公式识别`（从公式密集的 PDF / 图片提取 LaTeX）已在能力表中；
  托管架构下它跑在**服务端**，平板端零负担。相机为 Capacitor 标准插件。
- **错题本需要新的摄入路径**：现有 `hermes_core/learning/wrongbook.py` 的 `WrongbookService`
  是对**app 内答题记录（quiz attempts）与评估薄弱点（weak_points）的投影**，
  只覆盖"在 app 里做错的题"。平板版需新增**"从纸上来"的摄入路径**
  （拍照 → 识别 → 错题条目 → 复习队列）。**这是新开发，不是移植。**
- **场景价值**：拍纸质错题、而非在平板上重做一遍，是中国应试场景的高价值用法。

**对手写笔决策的理由更正**：§4.1 判定的"0.6.0 仅批注级"**结论不变，理由更正**——
它不是能力取舍或延期，而是**书写本就发生在纸上**。平板只需批注（圈画讲解材料）。
这同时解除了 Capacitor 选型下"webview 手写延迟最差"的隐患：该短板不在关键路径上。

### ⚠️ 本版最高优先级待验证假设

上述立场建立在一个假设上：**用户愿意保持"纸上做题"的习惯，
而非想要一个 GoodNotes 式的无纸化平板。**

**若该假设不成立**（用户确实想在平板上写数学），则技术栈选择直接暴露
（webview 是手写延迟最差的方案），§4.1 需整体复议。
**这是 0.6.0 最该优先验证的产品假设，重要性高于任何技术细节。**

> 附带记录（不影响本版做平板）：若"拍纸质作业"是核心桥梁，**手机在此动作上比平板顺手**
> （举起对准纸更容易），平板则赢在阅读与复习。形态权衡值得长期留意。

**In**
- 导师对话（带节奏、小步讲解、检查理解、answer-then-teach）
- STUDY 学习管线：课程空间、学习画像与路径规划（plan）、知识核（knowledge core）、
  知识库梳理、辅导（Tutor）、间隔重复闪卡（SM-2）、自测测验（确定性判分）、
  学习效果评估、数学与代码（公式↔代码 + 语义校验）、知识点捕获
- 读取用户上传的文件（服务端 Read 层）
- **拍照批改**：相机采集纸质作业 → 服务端公式识别/OCR → agent 批改讲评（一级能力）
- **错题本（含纸质摄入路径）**：拍照错题 → 识别 → 错题条目 → 复习队列；
  与既有 `WrongbookService` 的 app 内投影合流
- 批注级手写（Pointer Events + canvas，用于圈画讲解材料）
- 离线缓存复习类内容（闪卡 / 测验题 / 知识点）

**Out**
- REPORT（PPT / 文档生成、四层交付支线）
- Studio 路由
- 消息网关（0.5.0 已砍）
- 桌面端功能对齐（本版不承诺桌面与平板功能一致）

架构红利：读文件的重活（docling / 公式识别 / OCR）在服务端执行，桌面端"能力包按需下载
几 GB 模型"的机制在平板上直接消失。

### 4.1 客户端技术栈：Capacitor + React

**决定：Capacitor + React。不用 Tauri 2 mobile，不用 React Native / Flutter。**

推翻早期"沿用 Tauri 2 mobile"的倾向。那个倾向的前提是"复用桌面端的 Rust 命令层"，
但平板端是**瘦客户端**——不拉起 Python、不管进程、不守本地 learning.db，
**Tauri 最值钱的本地 Rust 侧在这个形态下无事可做**，前提已不成立。

选型的决定性约束是**内容形态**：本产品的学习内容是"**公式密集的教学文档**"——
数学贯穿全部受众段，且高数/考研数学以多行推导为教学形态（见 §2）。
现有依赖中 `katex` + `remark-math`/`rehype-katex`、`react-markdown` + `remark-gfm`
均为 Web 原生渲染，KaTeX 覆盖极完整且渲染失败有优雅降级。

> 注：`@codemirror/*`（代码编辑器）与 `highlight.js` 不构成本次选型依据——
> **代码学习不在 0.6.0 范围内**。早期论证曾以其为据，已作废。

- **React Native**：数学公式无成熟原生方案，最难的部分最终还是塞 WebView → 两头不讨好。
- **Flutter**：见下方专节评估。
- **Webview 系**：KaTeX / markdown **原样平移，不改一行**。

#### Flutter 备选评估（2026-08-13，经两轮修正后定案）

Flutter 曾被认真考虑并一度领先，最终未采纳。记录完整推理以备复议。

**Flutter 的真实优势（不收回）**：
- **自带渲染引擎，对大陆 Android WebView 碎片化免疫**——目标市场正是碎片化最严重处，这是实打实的加分；
- 滚动/动画手感与平板自适应布局优于 webview；
- 批注手写延迟低于 webview（虽仍非原生级）；
- 国内大厂广泛使用，生态成熟。

**曾被高估的 Capacitor 优势（更正）**：早期认为"Capacitor 插件生态碾压 Flutter"**不成立**。
Flutter 的 `in_app_purchase` 为官方包，极光/个推等聚合国内厂商推送的 SDK 均有官方 Flutter 插件。
内购/推送/国内 SDK 桥接两边**均成熟**，此项为平手，不构成选型依据。

**"一套代码通用于 Android 与 Apple" 不是选型依据**：该属性对 Flutter、Capacitor、
React Native、Tauri mobile 同时成立，仅排除"写两套原生"，不区分任何跨平台方案。

**决定性依据——学科范围**（见 §2）：数学贯穿全部受众段（高中数学 / 高等数学 / 考研数学），
高数与考研数学是公式最密集的内容类型，且其教学形态是**多行推导**。
而多行对齐（`aligned`）、矩阵/行列式（`pmatrix`/`vmatrix`）、分段函数（`cases`）、
重积分（`\iint`/`\oint`）**正是 LaTeX 子集渲染器最易出缺口之处**。
叠加**公式由模型现场生成、输入空间无法枚举**——子集渲染器一旦遇到未支持语法，
用户当场看到崩坏的公式，毁掉的是那一次教学。

**风险性质对比（最终裁决依据）**：
- WebView 碎片化（Capacitor 的风险）：**有解**——可测、可兜底（限定最低 WebView 版本，
  必要时内置 Chromium 内核）。
- 公式子集缺口（Flutter 的风险）：**基本无解**——唯一兜底是为公式单独开 WebView 渲染，
  等于把 webview 请回来，且落得每条公式一个 WebView 的性能问题。

**有解的风险优于无解的风险，故选 Capacitor。**

**复议条件（可证伪的 spike）**：以下构件全部由 `flutter_math_fork` 干净渲染，则 Flutter 重新入局；
其中**多行 `aligned` 失败即 Flutter 出局**（讲数学的基本盘）。测试语料应取自
现有 app 中**模型真实生成过的 LaTeX**（真实输入分布），而非手编用例。

```
\begin{aligned}                        多行推导对齐（最关键）
\begin{pmatrix} \begin{vmatrix}        矩阵与行列式
\begin{cases}                          分段函数
\lim_{x \to 0^+}                       带下标极限
\sum_{n=1}^{\infty}                    级数
\iint_D  \iiint_\Omega  \oint_L        重积分与曲线积分
\frac{\partial^2 f}{\partial x \partial y}   高阶偏导
P(A\mid B),\ E(X),\ D(X)               概率论记号
```

另建议一并实测：**真实小米平板上的 WebView 版本与兼容性**，量化 Capacitor 侧的已知风险。

webview 内部再比 Capacitor 与 Tauri 2 mobile：

| | Capacitor | Tauri 2 mobile |
|---|---|---|
| 移动端成熟度 | 生来移动端，多年量产 | 桌面强，移动是后补，明显更年轻 |
| 插件生态 | 大而全 | 薄，多数要自写 |
| **内购（本版必做）** | RevenueCat 官方 SDK + 成熟社区插件 | 基本 DIY |
| **推送（间隔重复提醒 = 刚需）** | 官方插件 + 大量前例 | DIY |
| 小米等国内厂商 SDK 桥接 | Kotlin/Java 插件写法文档完善、前例多 | 能做，路更生 |
| 二进制体积 | 略大 | 更小 |

本版必做**内购 + 推送 + 国内厂商 SDK 桥接**，正是 Capacitor 生态最厚、Tauri 最薄之处。
桌面端继续留在 Tauri 2 不受影响：两个壳职责已完全不同，真正共享的是 React 层，
只要传输层抽象干净就与壳无关。

**手写笔（批注级）**：WKWebView / Android WebView 均支持 Pointer Events，
Apple Pencil 与小米触控笔进来是 `pointerType: "pen"`，带压感（`pressure`）与倾斜（`tiltX/tiltY`）。
canvas 上做圈画、标错题、公式旁写两笔完全够用，且靠 `pointerType` 可过滤手掌误触。

**已知边界（0.6.0 不解决）**：webview 走事件循环 → JS → canvas 重绘 → 合成，
墨迹延迟明显高于原生 PencilKit（~9ms 级跟手感），连续书写整页推导手感不足；
PencilKit 墨迹引擎 / Scribble 在 webview 内够不着。
**注意：Flutter 并不能解决此问题**——它同样自绘 canvas、同样需 platform channel 桥接、
延迟同样非原生级。除纯原生（SwiftUI + PencilKit / Android Ink API）外，
所有跨平台方案的解法都是同一个：**写原生插件桥接 PencilKit**，而这件事在 Capacitor 上更好做。
故书写级手写留 0.7 作为独立能力立项（手写转 LaTeX 本身可独立成篇），不混入首版。

> 待核（本次规划时联网检索不可用）：各框架"当前成熟度"版本敏感结论、
> Google Android Ink API / 低延迟 stylus 方案的最新状态。落地前复核一次。

### 4.2 仓库策略：Open-core 拆分

**许可证前提**：现仓为 Apache-2.0，`kabuqina_core` 源自 Apache-2.0 的 hermes-agent 快照。
Apache-2.0 **允许基于其做闭源、商业、收费的衍生产品**（非 GPL，无传染性）。
唯一义务：衍生中保留上游 `LICENSE` / `NOTICE` 与版权头、注明改动。
故"平板产品闭源收费"在许可证上无障碍。

**方案 A（采纳）**：
- **公开仓（现仓）** 继续持有 `kabuqina_core`，保持 Apache-2.0。
- **新建私有仓** = 平板产品：Capacitor 客户端 + 托管后端 + 计费/IAP + 推理网关 + 提示词与业务逻辑。
  私有仓将 `kabuqina_core` 作为**依赖**引入（git submodule 或内部包）。

理由：① 核心本就公开且源自公开上游，转私有收益低；② 真正的护城河是**产品与业务层**
（后端、多租户、计费、提示词调优、UX），这些无任何开源义务，全部进私有仓；
③ 桌面端与平板端共用同一核心，避免 fork 两份各自打补丁。

建议布局（私有仓，全新历史——平板是重构，不必背现仓 git 历史）：

```
kabuqina-pad/           (private)
  apps/tablet/          # Capacitor + React 客户端
  services/backend/     # 托管后端（多租户 + 推理网关 + 计费）
  packages/core/        # submodule → 公开仓的 kabuqina_core
```

**安全提醒**：私有仓 ≠ 密钥安全。provider key、计费密钥、签名证书**一律不进 git**，
走密钥管理 / 环境变量。私有只意味着源码不公开，不意味着可以把密钥写进代码。

## 6. 里程碑（大陆为主，一步到位）

- **M0** `kabuqina_core` 重命名 + 瘦身落地（独立提交）；合规/备案由大陆 agent **并行启动**（外部）。
- **M1** 后端多租户化：核心上云、托管数据库、租户隔离。
- **M2** 账号 + 鉴权（含 Sign in with Apple）。
- **M3** 推理网关 + 计量 + 额度 + 限流。
- **M4** 平板客户端：导师对话 + STUDY（plan / 知识核 / 闪卡 / 测验 / 复习 / 画像），文件上传 + 离线缓存复习。
- **M4.5 拍照批改 + 错题本**：相机采集 → 服务端识别 → 批改讲评 → 错题入复习队列。
  **建议尽早验证**——它承载本版最高优先级的产品假设（§2 待验证假设），
  且是"纸负责动手、平板负责引导"定位能否成立的实证。
- **M5** 内购计费（IAP）+ 回执对账 + 额度联动。
- **M6** 内容审核对接 + 触控 / 横屏 UI 打磨。
- **M7** 上架：iOS 中国区 + 小米商店（后续扩华为/OPPO/vivo/应用宝），审核、灰度。

M1–M3（后端 / 账号 / 计量）必须先于 M4 客户端基本就位——瘦客户端没有后端即空壳。

## 8. 商业现实

- "$100/年撑到 1 万用户" 的旧目标**作废**。托管 + 平台垫推理，成本随用户线性涨。
- **应用内数字订阅强制走商店内购**：iOS 走 App Store IAP，苹果抽 30%；年营收 <100 万美元可入
  **Apple Small Business Program** 降至 **15%**。无教育类别通用折扣。安卓国内商店各有分成。
- 上架前需一张单位经济表：**每付费用户月推理成本 vs 订阅价 ×(1 − 抽成)**，否则用户越多亏越多。
- 计费系统要对接商店 IAP 回执做对账，不是简单接支付。
