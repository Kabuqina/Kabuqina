# v0.6.0 — 托管 Study 平板版规划（iPad + Android/小米）

状态：**草案 / 待评审**　·　日期：2026-08-13　·　目标版本：0.6.0

> 本文冻结 0.6.0 的形态判断与工作分解。DECISIONS.md 的正式条目见文末草稿，
> 需按 DECISIONS 的 "PR + 明确理由" 流程另行落地，本文不直接改 DECISIONS.md。

## 0. 一句话

0.6.0 不是"给桌面端套个平板壳"，而是**把 Study 学习内核从本地单机形态，重构为
云端托管的多租户消费产品**，在 iPad 和大陆 Android（先小米）上架、由平台提供推理并向用户收费。

## 1. 锁定决策

| 项 | 决定 |
|---|---|
| 平台 | iPad + Android 平板（Android 先上小米，逐步扩国内商店） |
| 市场 | **中国大陆** |
| 后端 | 云端托管多租户，跑 `kabuqina_core` |

| 产品面 | **只 Study**：导师对话 + 学习管线。REPORT / Studio / 网关均无 |

| 四层管线 | **保留**（学习支线）；仅移除其为 REPORT 服务的交付支线 |

## 2. 范围

**In**

- STUDY 学习管线：课程空间、学习画像与路径规划（plan）、知识核（knowledge core）、
  知识库梳理、辅导（Tutor）、间隔重复闪卡（SM-2）、自测测验（确定性判分）、
  学习效果评估、数学与代码（公式↔代码 + 语义校验）、知识点捕获

- 离线缓存复习类内容（闪卡 / 测验题 / 知识点）

**Out**
- REPORT（PPT / 文档生成、四层交付支线）
- Studio 路由
- 消息网关（0.5.0 已砍）
- 桌面端功能对齐（本版不承诺桌面与平板功能一致）

## 3. `kabuqina_core` 重命名 + 瘦身

**保留**

- **四层学习管线**：Read（读上传文件）→ Material Index → **Learning** Planner → Output Writer

机械但面广，单独成一块提交，配 grep 校验与迁移测试。DECISIONS.md 早已把此重命名记为
"延到 v0.4.0" 未做，借本次重构一次做掉。

## 4. 架构

```
┌── iPad / Android 平板（重构瘦客户端）──┐        ┌──────── 云端后端（全新）────────┐
│ React 前端（Tauri 2 mobile 承载）       │ HTTPS  │ 账号 / 鉴权（含 Sign in with Apple）│
│ ├ 导师对话                              │◀─────▶│ 多租户 kabuqina_core（按 owner 隔离）│
│ ├ STUDY：plan/知识核/闪卡/测验/复习/画像│ + WS   │ 四层学习管线（Read 在服务端跑重活）  │
│ ├ 文件上传 → 服务端 Read               │        │ 推理网关：平台持 key + 计量 + 额度 + 限流│
│ └ 离线缓存（复习内容）                 │        │ 学习数据层：learning.db → 托管数据库 │
└─────────────────────────────────────────┘        │ 内容审核 + 计费对账（IAP 回执）      │
                                                    └──────────────────────────────────────┘
```

架构红利：读文件的重活（docling / 公式识别 / OCR）在服务端执行，桌面端"能力包按需下载
几 GB 模型"的机制在平板上直接消失。

### 4.1 客户端技术栈：Capacitor + React

**决定：Capacitor + React。不用 Tauri 2 mobile，不用 React Native / Flutter。**

推翻早期"沿用 Tauri 2 mobile"的倾向。那个倾向的前提是"复用桌面端的 Rust 命令层"，
但平板端是**瘦客户端**——不拉起 Python、不管进程、不守本地 learning.db，
**Tauri 最值钱的本地 Rust 侧在这个形态下无事可做**，前提已不成立。

选型的决定性约束是**内容形态**：本产品的学习内容本质是"带公式和代码的文档"——
现有依赖里 `katex` + `remark-math`/`rehype-katex`、`react-markdown` + `remark-gfm`、
`highlight.js`、`@codemirror/*`（Python 课的代码编辑器）全是 Web 原生渲染。

- **React Native**：数学公式无成熟原生方案，CodeMirror 6 无对等物，最难的两块最终还是塞
  WebView → 两头不讨好。
- **Flutter**：`flutter_math_fork` 覆盖不全，代码编辑器弱于 CodeMirror 6，且 Dart 重写、零复用。
- **Webview 系**：KaTeX / markdown / CodeMirror **原样平移，不改一行**。

故选 webview 系。webview 内部再比 Capacitor 与 Tauri 2 mobile：

| | Capacitor | Tauri 2 mobile |
|---|---|---|
| 移动端成熟度 | 生来移动端，多年量产 | 桌面强，移动是后补，明显更年轻 |
| 插件生态 | 大而全 | 薄，多数要自写 |
| **内购（本版必做）** | RevenueCat 官方 SDK + 成熟社区插件 | 基本 DIY |
| **推送（间隔重复提醒 = 刚需）** | 官方插件 + 大量前例 | DIY |
| 小米等国内厂商 SDK 桥接 | Kotlin/Java 插件写法文档完善、前例多 | 能做，路更生 |
| 二进制体积 | 略大 | 更小 |

本版必做**内购 + 推送 + 国内厂商 SDK 桥接**，正是 Capacitor 生态最厚、Tauri 最薄之处。
桌面端继续留在 Tauri 2 不受影响：两个壳职责已完全不同，真正共享的是 React 层，
只要传输层抽象干净就与壳无关。

**手写笔（批注级）**：WKWebView / Android WebView 均支持 Pointer Events，
Apple Pencil 与小米触控笔进来是 `pointerType: "pen"`，带压感（`pressure`）与倾斜（`tiltX/tiltY`）。
canvas 上做圈画、标错题、公式旁写两笔完全够用，且靠 `pointerType` 可过滤手掌误触。

**已知边界（0.6.0 不解决）**：webview 走事件循环 → JS → canvas 重绘 → 合成，
墨迹延迟明显高于原生 PencilKit（~9ms 级跟手感），连续书写整页推导手感不足；
PencilKit 墨迹引擎 / Scribble 在 webview 内够不着。
**注意：Flutter 并不能解决此问题**——它同样自绘 canvas、同样需 platform channel 桥接、
延迟同样非原生级。除纯原生（SwiftUI + PencilKit / Android Ink API）外，
所有跨平台方案的解法都是同一个：**写原生插件桥接 PencilKit**，而这件事在 Capacitor 上更好做。
故书写级手写留 0.7 作为独立能力立项（手写转 LaTeX 本身可独立成篇），不混入首版。

> 待核（本次规划时联网检索不可用）：各框架"当前成熟度"版本敏感结论、
> Google Android Ink API / 低延迟 stylus 方案的最新状态。落地前复核一次。

### 4.2 仓库策略：Open-core 拆分

**许可证前提**：现仓为 Apache-2.0，`kabuqina_core` 源自 Apache-2.0 的 hermes-agent 快照。
Apache-2.0 **允许基于其做闭源、商业、收费的衍生产品**（非 GPL，无传染性）。
唯一义务：衍生中保留上游 `LICENSE` / `NOTICE` 与版权头、注明改动。
故"平板产品闭源收费"在许可证上无障碍。

**方案 A（采纳）**：
- **公开仓（现仓）** 继续持有 `kabuqina_core`，保持 Apache-2.0。
- **新建私有仓** = 平板产品：Capacitor 客户端 + 托管后端 + 计费/IAP + 推理网关 + 提示词与业务逻辑。
  私有仓将 `kabuqina_core` 作为**依赖**引入（git submodule 或内部包）。

理由：① 核心本就公开且源自公开上游，转私有收益低；② 真正的护城河是**产品与业务层**
（后端、多租户、计费、提示词调优、UX），这些无任何开源义务，全部进私有仓；
③ 桌面端与平板端共用同一核心，避免 fork 两份各自打补丁。

建议布局（私有仓，全新历史——平板是重构，不必背现仓 git 历史）：

```
kabuqina-pad/           (private)
  apps/tablet/          # Capacitor + React 客户端
  services/backend/     # 托管后端（多租户 + 推理网关 + 计费）
  packages/core/        # submodule → 公开仓的 kabuqina_core
```

**安全提醒**：私有仓 ≠ 密钥安全。provider key、计费密钥、签名证书**一律不进 git**，
走密钥管理 / 环境变量。私有只意味着源码不公开，不意味着可以把密钥写进代码。

## 6. 里程碑（大陆为主，一步到位）

- **M0** `kabuqina_core` 重命名 + 瘦身落地（独立提交）；合规/备案由大陆 agent **并行启动**（外部）。
- **M1** 后端多租户化：核心上云、托管数据库、租户隔离。
- **M2** 账号 + 鉴权（含 Sign in with Apple）。
- **M3** 推理网关 + 计量 + 额度 + 限流。
- **M4** 平板客户端：导师对话 + STUDY（plan / 知识核 / 闪卡 / 测验 / 复习 / 画像），文件上传 + 离线缓存复习。
- **M5** 内购计费（IAP）+ 回执对账 + 额度联动。
- **M6** 内容审核对接 + 触控 / 横屏 UI 打磨。
- **M7** 上架：iOS 中国区 + 小米商店（后续扩华为/OPPO/vivo/应用宝），审核、灰度。

M1–M3（后端 / 账号 / 计量）必须先于 M4 客户端基本就位——瘦客户端没有后端即空壳。

## 7. 外部依赖（不占本团队工时，但 gate 上架）

由大陆 agent / 团队负责，M0 起并行：

- 生成式人工智能服务备案 / 算法备案
- 软件著作权（软著）
- ICP 备案
- 内容审核能力（本团队负责**对接**，不负责取得资质）
- 数据境内存储 / PIPL 合规

**风险**：这些是行政周期（数周至数月），**任一未完成即封顶 M7 上架**。M0 不启动它，后续开发到位也上不了架。

## 8. 商业现实

- "$100/年撑到 1 万用户" 的旧目标**作废**。托管 + 平台垫推理，成本随用户线性涨。
- **应用内数字订阅强制走商店内购**：iOS 走 App Store IAP，苹果抽 30%；年营收 <100 万美元可入
  **Apple Small Business Program** 降至 **15%**。无教育类别通用折扣。安卓国内商店各有分成。
- 上架前需一张单位经济表：**每付费用户月推理成本 vs 订阅价 ×(1 − 抽成)**，否则用户越多亏越多。
- 计费系统要对接商店 IAP 回执做对账，不是简单接支付。
