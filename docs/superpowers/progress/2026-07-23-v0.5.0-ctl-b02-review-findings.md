## 2. `B02-R1` · 生产路径没有接管崩溃 operation

**位置：**

- `hermes_core/learning/learning_data_service.py:553`
- `hermes_core/learning/operation_coordinator.py:676`
- `python/src/desk_server/app.py`
- Gateway/cron/desktop startup 路径

**现状：**

`CompositeLearningDataService.recover_operations()` 已实现 phase recovery，但仓库中除测试外
没有生产调用者。若进程在 `delete`、`full_import` 或 `runtime_restore` 中崩溃，
`learning_operation_fences` 和 journal 会继续存在；重启后的普通读写只会持续返回
`learning_operation_in_progress`，不会自动接管。

同时不能简单让每个 Python child 在启动时无条件调用 recovery：desk、Gateway 与 cron 是
并行进程，后来启动的 child 不能把仍由存活进程执行的 operation 当作 crash 接管。

**修复要求：**

1. 明确唯一 recovery owner 和可证明旧 writer 已退出的接管时机。
2. 将 recovery 接入真实 desktop/Gateway 生命周期，而不是只在单测中直接调用 service 方法。
3. 存活 operation 不得被另一个正常启动的 child 抢占、回滚或提前 finish。
4. recovery 成功/失败须有不包含 owner 内容、checkpoint 或回答正文的 INFO/WARNING 日志。
5. 若需要改变 coordination schema 或 B01 已冻结的恢复合同，先更新设计/`DECISIONS.md`
   并重新审查，不能在实现中静默改变。

**必须新增的回归测试：**

- spawned process 在每个 durable phase 崩溃，走真实 restart/entrypoint 后自动接管；
- recovery 后 fence/journal 清理，最终状态符合 delete/import/restore phase 合同；
- 原 operation 仍存活时启动第二个 child，第二个 child 不得执行 recovery；
- recovery 重试幂等，失败时 fence/journal 保留且原因可观测。

## 3. `B02-R2` · Outbox projection 与 owner delete 存在穿插窗口

**位置：** `hermes_core/learning/learning_data_service.py:502-523`

**现状：**

`project_pending_outbox()` 分别执行：

1. 从 runtime DB 读取 pending event；
2. 向 `learning.db` 插入 projection activity；
3. 从 runtime DB 删除/标记 event。

三个步骤各自获取并释放 coordinator guard，没有一个 owner-wide guard 覆盖整个投影序列。
因此 owner delete 可以在步骤 1 与步骤 2 之间完成；随后 projection 又写回一条 activity，
形成 delete 后的数据复活。

**本轮复现结果：**

```text
projected 0
spaces 0
activities 1
orphan_detail {
  activity_kind: tutor,
  outcome: cancelled,
  terminal_code: user_cancelled,
  ...
}
```

即 owner 的 space/runtime 已全部删除，但 `learning_activities` 中重新出现了一条孤立记录。

**修复要求：**

1. 整个 pending-read → idempotent learning insert → runtime acknowledge 必须受同一个
   owner-wide coordination guard 保护。
2. 固定锁顺序仍为 coordination → learning → runtime，不得通过反向取锁修补。
3. delete/import fence 安装后不得产生新的 projection；delete 完成后不得重放删除前 event。
4. crash 可以留下 pending outbox 供安全重放，但不得产生重复或孤立 projection。

**必须新增的回归测试：**

- 两进程 barrier 精确卡在 list 后、insert 前，同时执行 owner delete；
- 同样覆盖 space delete；
- delete 返回后断言该 owner/space 的 spaces、activities、runtime rows、outbox 全为空；
- projection 在无 delete 竞态时仍保持幂等，重复 replay 只产生一条 activity。

## 4. `B02-R3` · `tutor_runtime_merge` 未校验合并后的总配额

**位置：** `hermes_core/learning/tutor_runtime_store.py:2443-2519`

**现状：**

`_normalize_import_bundle()` 只校验 incoming bundle 自身不超过：

- owner 非终态 12；
- space 非终态 6；
- checkpoint bytes 3 MiB；
- terminal runs、attempts、pending outbox 等各自上限。

`mode="tutor_runtime_merge"` 进入 transaction 后只处理 identity/idempotency conflict，
没有按“现有数据 + 实际新增数据”重新计算组合配额。

**本轮可重复复现：**

```text
before 12
merge {'runs': 12, 'checkpoints': 12, ...}
after 24
```

目标 owner 已有 12 个非终态 activity，再导入一个自身合法的 12 项 bundle，merge 成功，
最终保存 24 项，突破 `MAX_NONTERMINAL_PER_OWNER`。

**修复要求：**

1. 在同一个 runtime SQLite write transaction 内计算：
   `existing + incoming - exact idempotent duplicates`。
2. 对合并后的 owner/space 非终态数、terminal run 数、checkpoint bytes、attempt 数和
   pending outbox 数执行完整配额检查。
3. 任一配额或 identity conflict 必须整批 rollback，保持 zero-write。
4. exact idempotent duplicate 不应重复计数或错误拒绝。
5. 不得只依赖调用前的 bundle validation，因为校验与目标现状必须在同一 transaction 内完成。

**必须新增的回归测试：**

- existing 12 + incoming 1/12 非终态 → 拒绝且目标完全不变；
- existing space 6 + incoming 同 space 1 → 拒绝；
- existing checkpoint bytes 接近 3 MiB + incoming → 拒绝；
- terminal/outbox/attempt 组合上限；
- incoming 含 exact duplicates 时仅对实际新增项计数；
- batch 前半可插入、后半超限时整批 rollback。

## 5. `B02-R4` · Python/Rust canonical hash 对 Unicode 的处理不同

**位置：**

- `hermes_core/learning/tutor_contract.py:167-175`
- `hermes_core/learning/learning_data_service.py:26-27`
- `tauri/src/study.rs:453-460`

**现状：**

Python `canonical_json_bytes()` 会递归执行 Unicode NFC 规范化后再计算 SHA-256；
Rust `bundle_sha256()` 直接对 `serde_json::to_vec(bundle)` 的字节计算 SHA-256，没有 NFC
规范化。合法的 legacy/imported Study 数据可以包含分解 Unicode，因此 Rust 会把 Python
生成的正确 bundle/hash 误判为 `prepared bundle hash is invalid`。

**本轮复现向量：** bundle 中包含分解形式的 `Cafe\u0301`。

```text
Python canonical: 9c6214595d095d55865200df09242eb20e3e14067aad8553d83b7bf29613f09c
Rust-like JSON:   0d7026b74b93b2b0aa7691d0f0371763cb5567617a58deb005010bf5133e4dee
```

**修复要求：**

1. Python 与 Rust 必须共享完全一致的 canonical contract：NFC、key ordering、
   compact UTF-8、number restrictions 和 normalized-key collision 行为。
2. 不得通过跳过本地 hash/readback 验证来规避差异。
3. prepare 写盘失败或 hash 不一致时仍须保持 runtime 数据不删除。

**必须新增的回归测试：**

- NFC 与 NFD 等价字符串生成同一跨语言 hash；
- object key 顺序变化生成同一 hash；
- normalized key collision 按 Python 合同拒绝；
- 包含中日韩文字、组合音标和 emoji 的 BundleV2 完成写盘、回读和 commit；
- Python 固定向量与 Rust focused test 使用同一组 fixtures。
