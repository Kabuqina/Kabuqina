## Canonical 原型交互 → v0.5.0 生产状态（owner，2026-07-28）

这张表用于把“原型里点得动”与“v0.5.0 真实可交付”分开。Claude 做生产前端时按三档处理：

- **必须真实**：读取/写入权威数据，重启后仍成立，失败有真实错误状态；不得用 fixtures、
  `localStorage` 或成功 toast 冒充后端完成。
- **可明确模拟**：只允许留在 canonical 原型和评审工具中，并且必须有模拟标识；合入生产
  `web/` 时要么接成真实能力，要么去掉该动作。
- **明确推迟**：v0.5.0 不提供可点击入口，也不为了占位先造后端空合同。

## B-10 `P0` 全局 Activity 与重启恢复投影 — **后端缺口已确认**

**前端形态：**全局 Activity 面板读取一份跨域状态列表，至少能区分 `Study` / `Studio`、
`running` / `waiting` / `interrupted` / `failed` / `completed`，并给出“回到现场”；只有底层
活动真的支持 resume/retry 时才显示对应动作。J5 重启后应能同时列出可区分的 Course 与
Project 现场，由用户选择，而不是偷偷恢复最近一个。

**核过代码后的缺口：**现有
`GET /api/desk/study/activity-runs` 与 `cmd_study_activity_list` 必须同时给出一个
`space_id` 和一个 `activity_kind`，只能查询单门课程、单类活动；仓库里没有
`/api/desk/activity`、全局 Tauri command 或 Studio activity/recovery 合同。Study 的 checkpoint、
`waiting_for_learner`、interrupted 与 resume 真值已经持久化；Studio 目前只有 Project / Brief /
来源快照与 `stage`，**不能把一个 Project 猜成“后台正在运行”**。

**建议的最小调用合同：**

| 命令 | 入参 | 返回 |
|---|---|---|
| `cmd_activity_records` | `{ statuses?: ActivityStatus[], limit?: number }` | `{ items: ActivityRecord[], count, limit }` |

`ActivityRecord` 至少包含
`id / domain / kind / status / title / updatedAt / returnTarget / fallbackTarget /
canResume / canRetry`。`domain ∈ study|studio`。Study 记录从已有 activity/checkpoint 投影；
Studio 只有在未来出现真实长任务时才投影任务。当前 Project 的 J5 恢复项若进入同一列表，
必须用独立 `kind: "project_scene"` + `status: "recoverable"` 如实表达，不能复用 `running`。

**后端要动：**建议在桌面集成层新增
`python/src/desk_server/routes/activity_routes.py` 并在 `desk_server/app.py` 注册；新增
`tauri/src/activity.rs` 并在 `tauri/src/lib.rs` 注册 command。Study 投影读取
`hermes_core/learning/tutor_runtime_store.py` 的持久化记录；Studio 可恢复现场读取
`python/src/studio_store.py`，不复制两边领域数据。Web 包装由 S10 放在自己的 Activity 模块。

**现成写法可抄：**Study 生命周期动作与错误映射直接照
`python/src/desk_server/routes/study_activity_routes.py` + `tauri/src/study.rs`；Project 列表与
确定性返回入口照 B-7/B-8。聚合路由只负责投影与排序，不拥有 Course、Project 或 checkpoint。

**验收：**

- 新装用户返回空列表而不是错误；
- 两门 Course 的中断活动能在一次查询中同时出现，domain、Course 标题与返回位置正确；
- Studio Project 可作为“可返回现场”出现，但没有真实任务时绝不显示为运行中；
- restart 前后的稳定 id、状态与 return target 一致；目标失效时走 `fallbackTarget`；
- resume/retry 仍调用领域原命令并校验 revision，不由聚合接口私自改状态；
- completed 默认只保留有限的近期记录，Activity 不能退化为另一份无限历史库。

## B-11 `P1` 自由 Chat → Studio 的审核快照 — **入口出现才实施**

**前端形态：**只在未绑定 Course / Project 的自由 Chat 中提供“送入 Studio”。用户先选 Project，
再预览将带走的消息，确认后写成一份只读来源快照并回到该 Project。Course Chat 没有出口；
Studio Chat 本来就在 Project 内，也不借这个入口复制自己。

**核过代码后的缺口：**`web/src/studio/studio-api.ts` 虽然把快照 `kind` 预留为
`chat_session`，但输入 `StudioSourceRef` 只有 `study_artifact`；`tauri/src/studio.rs` 与
`python/src/desk_server/routes/studio_routes.py` 都会明确拒绝其他 kind。当前 Chat message 行也没有
可供前端长期保存的稳定 message id，因此不能让 UI 凭临时数组 id 假装完成可追溯选择。

**建议的 v0.5.0 最小合同：**扩展现有 `cmd_studio_gather_sources`，把 `StudioSourceRef` 改为
判别联合：

```ts
type StudioSourceRef =
  | { kind: "study_artifact"; spaceId: string; artifactId: string }
  | { kind: "chat_session"; sessionId: string; messageIndexes: number[] };
```

`messageIndexes` 只标识用户在提交预览中选中的持久化 transcript 行；后端必须重新读取 session
消息并生成 `title / origin / excerpt / returnTarget / fallbackTarget`，不能相信前端上传的正文。
同一次提交仍保持原子性。若实现前决定给 message 表补稳定 row id，可把 indexes 换成 ids，
但不能沿用只存在于 React state 的 `UiMsg.id`。

**后端要动：**`python/src/desk_server/routes/studio_routes.py` 增加自由 session 解析与快照生成；
`tauri/src/studio.rs` 把固定 struct 改为受校验的 enum；`web/src/studio/studio-api.ts` 更新联合类型。
`python/src/studio_store.py` 已能保存任意合法 `kind` 的不可变快照，表结构无需新增第二套来源表。

**现成写法可抄：**权威 transcript 读取见
`python/src/desk_server/routes/sessions.py::get_session_messages`；Study 来源的后端生成与原子写入
见同一个 `studio_routes.py::_resolve_study_sources` / `StudioStore.add_sources_atomic`。

**验收：**只允许真实存在且未绑定的自由 session；拒绝 `study:*`、`studio:*` 与不存在的 session；
消息索引越界、空选择、超过快照上限时整批失败且不留下部分来源；快照重启后仍在，可返回原 Chat；
删除原会话后快照正文仍可读，但返回入口降级到 Chat 历史；项目删除仍不删除原会话。

**范围开关：**如果 v0.5.0 不准备实现本条，Claude 就不要在生产 Chat 放入口；这不会阻塞
B-7 的 Studio 从 Study 取材，也不允许用“即将推出”按钮占产品主路径。

2. **项目删除返回确定性解绑信息。**新增

## B-9 `P1` 多材料对齐：骨架提名 + 挂靠 + 角色（**agent 能力，不是 CRUD**）

**设计定稿见架构 §2.1.2**（2026-07-27）。这一条与账本里其他项不同：它要的不是一个接口，
而是一次**可核对的判断**。先读那一节再动工，尤其是四条红线。

**要产出的判断（四件事，都必须给可核对的理由）：**

1. **分课** — 导入的这批文件是不是同一门课？不是就拆成多个课程本，不硬凑一个目录。
2. **选骨架** — 提名一份有真实可抽章节结构的文件，**并给理由**
   （"它有 12 章目录，且其他三份都能挂上去"）。**提名，不是决定**：学生一步确认或换一份。
3. **对齐 + 角色** — 其他文件逐项挂到骨架的节上（「习题集 p.41 → §2.3」），
   并判定角色 `讲解 | 练习 | 检验 | 参考`。角色决定它进学习循环的哪一步。
4. **落不下的显式留白** — 挂不上就标"还没对上"，**不强配、不隐藏**。

**为什么形态必须是"声明对应"而不是"生成目录"：**目录的可信基础是"整理既有结构、
不凭空生成关系"（§2.1.1），界面上写着「小娜从《…》整理」。合成一棵主题树会让这句话
变成谎话，且学生无法核对某个节从哪来。**对应可以被学生打开两边验证，发明不能。**

**必须走草稿箱：**挂靠与角色都是 draft，学生确认后才生效——与知识点、卡片、计划同一条
通道（§2.1.1 已确立"只有闪卡与测验直接激活，计划/知识库/资源包仍停在 draft"）。
**不要为这条开自动激活的后门。**

**现成写法可抄：**docling 已能抽 PDF/DOCX/PPTX 结构；草稿箱与激活链见
`hermes_core/learning/learning_plans.py` 的 `activate_plan` / `reject_plan` /
`_materialize_items`；artifact 审核状态见 `study_routes.py` 的
`/api/desk/study/artifacts/{id}/status`。

**后端数据形状已定并实现（2026-07-28）：**使用一个原子化
`kind: "material_alignment"` draft artifact 承载整批判断，避免“骨架已确认、挂靠仍是旧版”的
分裂状态。`payload` 包含：

- `materials[]`：材料及其**真实抽取**的 `structure[]`（`section_id / title / locator`）；
- `course_groups[]`：分课结果，每组含 `proposed_title / rationale / material_ids`；
- 每组一个 `skeleton`：真实材料 id、角色、提名理由；
- `attachments[]`：材料角色与理由，以及节/页范围级 `mappings[]`；目标只能是该骨架已有的
  `section_id`；挂不上的范围进 `unaligned[]` 并给理由；
- `ungrouped[]`：无法归课的材料与理由，不允许隐藏；
- 角色的稳定存储值为 `explanation | practice | assessment | reference`，界面翻译为
  「讲解 / 练习 / 检验 / 参考」。

Agent 通过专用工具 `learning_material_alignment_propose` 提交。后端严格验证每份材料恰好归入
一个课程组或 `ungrouped`、骨架确有真实结构、所有映射只指向真实骨架节；同时禁止任何
`coverage` 字段。该 artifact 强制 semantic review，只有学生确认后才能激活。

**激活的边界：**本轮激活确认的是“这批分课/骨架/挂靠判断”，不自动创建空课程本，也不搬运
尚不存在的材料记录。前端/后续导入编排可在确认后按 proposal materialize，不能在确认前产生副作用。
单文件仍走现有导入路径，不调用该工具（工具也拒绝少于两份材料）。

**验收：**
- 单文件导入的行为**完全不变**（这条不能把现有单教材路径搞复杂）；
- 两份以上时能提名骨架并给出理由；
- 挂不上的文件仍然出现在书堆里且标注"还没对上"；
- 任何一处都不出现覆盖率/对齐百分比；
- 学生不确认，挂靠不生效。

## B-12 `P1` 杂记本：一本不属于任何课程的本子 — **后端已实现，前端契约已接通**

**设计定稿见 design-qa Iteration 10 与 12**（原型 `ScratchNotebook`）。动工前先读那两节，
尤其是「杂记本是**留白**，不是待办箱」这条——它决定了下面所有验收标准。

**原始缺口（实现前核对）：这个东西后端一点都没有。**

- `hermes_core/learning/learning_store.py` 的 `learning_spaces` 表只有
  `owner_id / space_id / title / status / is_current / created_at / updated_at`，
  没有任何区分"这不是一门课"的字段；
- `hermes_core/learning/learning_contract.py` 的 `KINDS`（L47 起）九种 artifact 里
  没有一种承载自由随手写；
- `python/src/desk_server/routes/study_routes.py` 全部 `_desktop_ctx(space_id=...)`
  按课程作用域，没有"无课程"这一路。

### 已实现的形状（前端既有留位不需要改合同）

**把杂记本实现成一个保留的 space，而不是第二套存储。** 理由：artifact、草稿、持久化、
备份导出/导入这一整套管道可以原样复用，也不会出现"同一对象在两处各有一份可变副本"
（架构 §8 不变量 3）。它"不是课程"是**产品行为**上的——没有计划、没有卡片、没有五分页、
不计数——不必是存储层的另起炉灶。

使用显式字段让前端把它从课程里分出来：

| 变更 | 位置 | 说明 |
|---|---|---|
| `learning_spaces` 加 `kind` 列 | `learning_store.py` L592 起 `create_space` / L644 `list_spaces` | `'course'` \| `'scratch'`，默认 `'course'`；旧库缺列时按 `'course'` 读，无需数据迁移 |
| `_space_payload` 带出 `kind` | `study_routes.py` L183 | 前端 `repository.ts` L307 的 mapper 已经在读 `space.kind`，缺失时回落 `"course"` |
| 每个 owner 幂等种一本杂记本 | `scratch_notebook.py` | 稳定 owner-scoped id；`create_space(..., make_current=False)`，不抢当前课程 |

**本轮落地（2026-07-28）：**`learning_spaces.kind` 已由 declarative reconcile 自动补列，
旧记录默认 `course`；`GET /api/desk/study/spaces` 幂等确保每位 owner 有且仅发现一本
`scratch`。杂记本永远不能被设为 current course，Web 打开它时也不调用课程 select 命令。
随手写与来自 Chat 的条目复用 `learning_items`，因此随 Study 导出/导入和删除链一起持久化，
没有另建第二套数据库。

归本在一个 owner-wide SQLite 写事务中完成：先验证源是 `scratch`、目标是 `course`，再把
该条转成目标课程里的 `knowledge_base` semantic-review draft，最后删除源条目。任一步失败
都会回滚，杂记本里的原条目不丢。所有普通课程路由拒绝 scratch space，防止它长出计划、
卡片或五分页数据。

**现成写法可抄：**建表与列增见 `learning_store.py` 自己的建表段；幂等种子见
`builtin_course_seed`；路由与命令链见 `study_routes.py` 既有的 spaces 那几条。

### 前端将要怎么调

| Web 包装 | 入参 | 返回/说明 |
|---|---|---|
| `cmdStudySpaces()`（**已存在**） | — | 每个 space 多一个 `kind`；前端据此把杂记本挪到书立最右侧 |
| `cmdStudyScratchGet(spaceId)` | — | `{ pad: string, notes: ScratchNote[] }` |
| `cmdStudyScratchSavePad(spaceId, pad)` | 全文覆盖 | 随手写就一页纸，不做增量 diff |
| `cmdStudyScratchFileNote(spaceId, noteId, targetSpaceId)` | — | 把这条**归到某一本课程本**，在目标课程建 draft artifact 并从杂记本移除 |

`ScratchNote = { id, text, origin, createdAt }`。`origin` 是给学生看的来源短语
（「来自对话」），**不是** session id——内部对象名不进学生可见层。

### 四条红线（产品，不是技术）

1. **不计数。** 不返回条数、不返回未整理数、不给徽章。接口里出现 `count` /

2. **归本是安静的可选动作。** 后端不排序、不推荐、不催。
3. **归本后仍是 draft。** `cmdStudyScratchFileNote` 在目标课程建的是待审核 draft，

4. **不做搜索、标签、排序、批量操作。** Iteration 10 明确列为「deliberately not built」。

### 验收

- 新装用户第一次打开 `/study` 时杂记本已存在且**不是**当前课程（不抢 `is_current`）；
- 杂记本不出现在任何"选一门课"的列表里（Chat 保存到、Studio 取材、计划、卡片）——

- 旧库升级后 `kind` 缺失的 space 一律按课程读，界面不变；
- 归本后：这条从杂记本消失，在目标课程里是 draft 而非 active；
- 任何返回里都没有条数。

**前端当前状态（2026-07-28）：**书立的杂记本标签、牛皮纸页、随手写、归本流程与窄窗
工具条已按上表实现；后端现在会真实返回 `kind: "scratch"`，三个既有 Web wrapper 已接到

## B-2 `P1` 导入精读档位的默认值 — **后端已实现；前端可接入**

**核过代码后的结论与规格初稿不同，先说清楚：**`read mode` 目前**根本不存在"用户默认值"
这个概念**。它是**模型每次自选的工具参数**——`hermes_core/tools/document/schemas.py`
里 `mode` 的 description 直接写给模型看（"DEFAULT to mode=auto … only escalate to the
much slower mode=precise/math when the user explicitly needs …"），
`reading.py::_docling_profile_for_mode`（L304）按每次调用的入参解析。

**因此这不是"把设置接上已有旋钮"，而是要先造旋钮。** 后端已采用原建议 (b)，但把
作用域严格限制在可信的 Study 材料读取命令：

- 偏好值为 `auto | precise | math`，默认 `auto`；既是导入默认值，也是该路径的计算上限；
- 导入界面可以用一次性的 `overrideLimit: true` 明确越过上限；
- 普通 Chat 的 `document_read_precise` / `pdf_read_precise` 完全不改，用户在对话中明确要求
  精读仍然有效；模型不能自行伪造这个可信 UI override。

**Claude 接线契约：**

| Web 包装 | 入参 | 返回/说明 |
|---|---|---|
| `cmdStudyPreferencesGet()` | — | `StudyPreferences`，含当前值和 `defaults` |
| `cmdStudyPreferencesPut(patch)` | `importReadMode? / dailyNewCardLimit? / dailyReviewCardLimit?` | 支持局部更新，返回完整偏好 |
| `cmdStudyMaterialRead(input)` | `pathStr / requestedMode? / overrideLimit? / includeContent? / pageStart? / pageEnd?` | 返回 `preferredMode / requestedMode / effectiveMode / limited / override / result` |

设置页只需读写 `importReadMode`。材料导入未显式选档时不传 `requestedMode`；临时选了比偏好
更重的档位时，先展示性能提示，再由学生确认后传 `overrideLimit: true`。如果未确认，后端会
降到偏好档位并以 `limited: true` 明示，不会静默把 CPU 推理跑起来。

**为什么值得做：**auto 是 pypdf 秒级，precise/math 是 CPU 推理，差一个数量级。
学生导一本 300 页教材撞上 precise 会以为程序卡死。见记忆 `docling-read-modes-and-perf`。

**前端已留位：** 设置 →「高级」tab，一个三档选择器；现在可以按上述命令直接接入。
