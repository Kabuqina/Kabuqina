## B-1 `P1` token 用量聚合 — **本轮后端已实现；Study 仍在开发**

**前端形态：** 设置 →「模型」tab 一节，**只报 token 数，不折算金额**
（owner 定：定价/折扣/缓存命中都不在我们手里，报假精度的钱比不报更糟）。
按**本周 / 本月 + 按课程分组**展示，低强调数字，不做趋势图。

**好消息：数据已经落库，不需要新埋点。**
`hermes_core/learning/tutor_runtime_store.py` 的 `tutor_provider_attempts` 表
（建表在同文件 L214 起）已有：

| 列 | 用途 |
|---|---|
| `actual_input_tokens` / `actual_output_tokens` | 要聚合的量（可空，失败的 attempt 为 NULL） |
| `owner_id` / `space_id` | 按学生 / 按课程分组 |
| `provider_id` / `model_id` | 按模型分组 |
| `status` | `reserved`/`succeeded`/`failed`/`unknown`，只算 `succeeded` |
| `reserved_at` / `completed_at` | 时间窗口 |

**本轮已实现的四段：**

1. **store 聚合方法** — `tutor_runtime_store.py`。
   **现成写法可抄：**同文件 `_attempt_fold`（L1566 起）已经在
   `SELECT COUNT(*) … COALESCE(SUM(reserved_input_tokens),0) … FROM tutor_provider_attempts
   WHERE owner_id=? AND space_id=? …`，照它把 `actual_*` 加进去、把 `WHERE` 放宽到
   时间窗口、`GROUP BY space_id, model_id` 即可。
2. **desk 路由** — `python/src/desk_server/routes/study_routes.py`。
   **现成写法可抄：**同文件 `study_data_export`（`@router.get("/api/desk/study/data/export")`）
   那一小段的 `_desktop_data_service()` + `_http_error` 模式，五行。
   建议路径 `GET /api/desk/study/token-usage?window=week|month`。
3. **tauri command** — `tauri/src/study.rs` + `tauri/src/lib.rs` 注册。
   **现成写法可抄：**`cmd_study_data_export`（`study.rs` L691）就是同形状的
   `desk_json_request_structured(&app, Method::GET, "/api/desk/…", None)`。
4. **web 包装** — `web/src/chat/study/study-api.ts` 加一个 `cmdStudyTokenUsage()`。

**验收：** 只统计 `status='succeeded'`；NULL 不当 0 混入平均值；跨课程求和 = 各课程之和；

## B-7 `P0` Studio 项目持久化 — **当前后端契约已实现；Studio 前端仍未完成**

**本轮落地状态：**项目 SQLite 持久化、brief 保存、Study 原对象只读解析、原子化素材
快照，以及 Python → Tauri → Web 命令链已经在 `codex/v050-backend-requirements` 实现并验证。
这只解决了截至本次盘点已经明确的后端阻塞；**Studio 前端仍有功能未完成**，后续契约与
后端缺口继续追加到本文。

**当前已接入的前端部分按这份契约调用。**
契约在 `web/src/studio/studio-api.ts`，三个命令：

| 命令 | 入参 | 返回 |
|---|---|---|
| `cmd_studio_projects` | — | `{ projects: StudioProject[] }` |
| `cmd_studio_create_project` | `{ title }` | `StudioProject` |
| `cmd_studio_save_brief` | `{ projectId, brief }` | `StudioProject` |

`StudioProject = { id, title, brief, stage, createdAt, updatedAt, sources[] }`，
`stage ∈ brief|gathering|shaping|review`。`sources` 是 `StudioSourceSnapshot[]`，
字段严格照架构 §4.2：`id / kind / title / origin / excerpt / createdAt / revision /
returnTarget / fallbackTarget`。

**现成写法可抄：**整条链与 Study 完全同形——
`python/src/desk_server/routes/study_routes.py` 的路由风格、
`tauri/src/study.rs` 的 `desk_json_request_structured`、
`web/src/chat/study/study-api.ts` 的包装。存储可仿 `learning` 那套 SQLite。

**不变量（架构 §8，实现时必须守住）：**

1. Studio **引用**快照，不拥有也不改写 Study 原对象；
2. Studio 产出**不得**自动修改学习状态 / 掌握度 / 计划完成度；
3. 同一对象不得在两域各有一份可冲突的可变副本；
4. restart 后多个 Project 现场可区分、可恢复。

**取材流程（§4.1）前端已完整实现，只差最后的写入命令：**

选课程 → 选内容 → **预览将取走什么** → `cmd_studio_gather_sources` → 回到项目。
前两步读的是**真实 Study 数据**（`cmdStudySpaces` / `cmdStudyArtifactSummaries`），
不是 mock；预览步骤逐条摊开将要生成的快照。缺的只有第四步。

| 命令 | 入参 | 返回 |
|---|---|---|
| `cmd_studio_gather_sources` | `{ projectId, refs: StudioSourceRef[] }` | 更新后的 `StudioProject` |

`StudioSourceRef = { kind: "study_artifact", spaceId, artifactId }`。

**注意前端交的是引用不是内容**：正文不经前端搬运，由后端读 Study 原对象生成快照
（§4.2）。`excerpt` / `origin` / `returnTarget` / `fallbackTarget` 都由后端填。

失败时前端已保证"什么都没有带走"的措辞与状态，**所以这个命令必须是原子的**：
要么全部快照建成，要么一条都不建，不允许部分成功。

**验收：**新装用户打开 `/studio` 看到空项目册而不是错误；建项目→写 brief→重启后仍在；
`cmd_studio_projects` 在没有任何项目时返回 `{projects: []}` 而不是报错。

## B-8 `P1` Studio Chat 的项目作用域会话

**前端已完成并可独立工作**（handoff、作用域条、返回与解绑都在前端），
但有两件事只有后端能做：

1. **会话 id 需要被后端接受。**项目会话用确定性 id `studio:<projectId>`
   （`resolveStudioChatSessionId`），与 Study 的 `resolveStudyChatSessionId` 同策略。
   若后端对 session id 有格式校验（如 `validate_id` 只放行
   `[A-Za-z0-9._:-]`），`studio:p1` 这种带冒号的要确认放行——
   Tauri 侧 `studio.rs::validate_id` 已经允许 `:`，desk 侧请一并确认。
2. **项目删除时要能清掉对应会话**（或至少让它优雅失效）。前端目前只在删会话时
   解绑作用域；反方向——项目没了、会话还挂着——需要后端在删项目时告知，
   否则会留下指向不存在项目的"回到项目"按钮。**项目删除命令本身也还没有。**

**顺带提一句契约：**Chat 与 Studio 之间**不需要**新的内容通道。转交只带项目标题、
brief 和已取素材的**标题**；素材正文不随转交搬运（与 §4.2 同一条原则）。

**验收：**绑定项目会话后重启应用，回到该会话仍显示项目作用域；删除项目后不留下
指向死项目的返回入口。

## B-2 `P1` 导入精读档位的默认值

**核过代码后的结论与规格初稿不同，先说清楚：**`read mode` 目前**根本不存在"用户默认值"
这个概念**。它是**模型每次自选的工具参数**——`hermes_core/tools/document/schemas.py`
里 `mode` 的 description 直接写给模型看（"DEFAULT to mode=auto … only escalate to the
much slower mode=precise/math when the user explicitly needs …"），
`reading.py::_docling_profile_for_mode`（L304）按每次调用的入参解析。

**因此这不是"把设置接上已有旋钮"，而是要先造旋钮。** 需要 Codex 决定并实现其中一种：

- **(a) 偏好注入 prompt**：把学生的默认档位写进工具描述或系统提示，模型仍可覆盖。
  改动小，但保证弱——模型可能不听。
- **(b) 硬上限**：在 `reading.py` 入口把超出默认档位的请求降级，除非调用方显式带
  `override=true`。保证强，但会让"我就是要精读这一页"变难。
- **推荐 (b) 但只作用于"导入"这一条路径**，对话里显式要求精读不受限。

**为什么值得做：**auto 是 pypdf 秒级，precise/math 是 CPU 推理，差一个数量级。
学生导一本 300 页教材撞上 precise 会以为程序卡死。见记忆 `docling-read-modes-and-perf`。

**前端已留位：** 设置 →「高级」tab，一个三档选择器。后端契约定了我再接。
